## Dependencies & Execution Order

### Phase Dependencies

- **Setup (Phase 1)**: No dependencies — start immediately
- **Foundational (Phase 2)**: Depends on T001 — BLOCKS both user stories
- **User Story 1 (Phase 3)**: Depends on Phase 2 (needs both the data key and the filter)
- **User Story 2 (Phase 4)**: Depends on Phase 2 AND on T004 from US1 — its checks read the rendered output
- **Polish (Phase 5)**: Depends on Phases 3–4

### Task-Level Dependencies

```text
T001 → (T002 ∥ T003) → T004 → T005 → T006
                          └──→ T007 → T008 → T009 → T010 → T011
```

T007–T009 all mutate `src/_data/site.json` and must run sequentially. T005/T006 and T007 may interleave once T004 is done, but each rebuild overwrites `public/`, so running them in order avoids confusing intermediate states.

### Parallel Opportunities

- **T002 ∥ T003** — different files (`src/_data/site.json` vs `eleventy.config.js`), no mutual dependency. This is the only genuine parallel pair; the feature is otherwise a single sequential thread through three files.

### MVP First (User Story 1 Only)

1. Complete Phase 1 (T001) and Phase 2 (T002–T003)

### Incremental Delivery

The whole feature is a single sitting for one implementer (~3 file edits + verification): T001 → T011 in order, with T002/T003 in parallel if convenient. Checkpoints after Phase 3 and Phase 4 are natural commit points.
